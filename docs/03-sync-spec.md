# 同步（WebDAV）技术方案

适用版本：0.5.0

## 1. 问题定义

Summa 的文献库是单个 `library.json`。同步要在两台（或多台）机器之间保持它一致，而 WebDAV 只是一块可以读写文件的网盘——没有变更流、没有合并语义、没有事务。所有一致性都得自己实现。

最容易想到的做法是「比时间戳，新的一方覆盖旧的一方」。这个做法有一个致命缺陷：**两台各加一篇，后同步的那台会把先同步的那篇整库覆盖掉，而且是静默的**。用户不会收到任何提示，只会在某天发现文献少了。

所以本方案不做整库覆盖。

## 2. 四条规则

### 2.1 取并集

按文献 `id` 合并，两边各自独有的记录都保留。这是唯一能保证「两边各加一篇都不丢」的做法。

`id` 的生成方式是 `p{毫秒时间戳}`，两台机器同毫秒生成的碰撞概率可以忽略；外部工具导入时还会拼上当前库长度。

### 2.2 同一篇以 `rev` 大的一侧为准

`Paper` 增加 `rev` 字段（毫秒时间戳）。理论上可以按字段合并（标签取并集、笔记取更长的），但那样用户无法预测结果，出了问题也没法解释。整条记录取新，行为可预期。

`rev` 的写入点只有一个：`commit_library()`。它在每次写库前逐篇比对序列化结果，内容变了就刷新 `rev`。这样做的理由是**不能依赖命令自己记得刷新**——漏掉一处，表现就是「这台机器的修改被另一台覆盖」，而这种问题极难定位。

老数据没有 `rev`，用 `added` 兜底（`sheet_rev = max(rev, added)`）。两者都是毫秒时间戳，可以直接比较。

### 2.3 删除用墓碑

只删记录不删远端，另一台机器下次同步会把它当成「只存在于远端」再传回来。所以删除时写入墓碑 `{id, at}`，墓碑参与同步、取并集。

**墓碑优先于存在**：只要 id 在墓碑集合里，这篇就一律移除，不论另一台机器上的版本多新。

这个取舍的代价必须说清楚：A 机删了某篇、B 机恰好也改了它，以删除为准，B 的修改会丢。反过来的设计（较新的修改胜过删除）会导致「删了又回来」，而用户对复活的反感远大于对冲突提示的容忍。选删除优先，是因为删除是明确的一次用户动作，而「改了又删」是自相矛盾的操作序列。

墓碑上限 1000 条，超出按时间裁剪。每条几十字节，不会让文件膨胀。

### 2.4 路径不上传

`file` 和 `source` 是本机绝对路径。上传前清空，下载后按 `files/{id}.pdf` 重建。

不清空的话，A 机的 `/Users/a/Library/.../p123.pdf` 会漂到 B 机上，覆盖掉 B 本来能用的路径——表现是「同步之后 PDF 打不开了」。

合并时还要防止反向污染：如果本地已有可用路径，即使采用了远端的记录，也要把本地的路径补回去。

## 3. 流量控制

同步每开一次应用就跑一次，不能每次都把整库传一遍。

- **远端有没有变**：用 `HEAD` 取 `ETag`，与上次同步记录的值比较；服务端不返回 ETag 时退回 `Last-Modified`
- **本地有没有变**：把要上传的内容做 FNV-1a 哈希，与上次记录的哈希比较

两边都没变就跳过整个传输，一次同步只有几个 `HEAD` 的往返。

不用 `PROPFIND`，因为它要解析 XML，各家实现的命名空间差异会带来无谓的调试成本；`HEAD` 足够判断单个文件是否变化。

## 4. PDF 原文

PDF 单独存放，靠 `pdf-index.json` 记录「远端有哪些 id 的原文」，而不是对每篇做一次 `PROPFIND` 或 `HEAD`。几百篇文献的情况下，逐篇探测会产生几百个请求，群晖之外的 WebDAV 服务（如坚果云）有请求频率限制，会直接失败。

流程：

1. 读 `pdf-index.json`（一次 GET）
2. 本地有、远端没有 → 上传
3. 远端有、本地没有、且这篇仍在文献库里 → 下载，回填 `file`
4. 索引收窄到仍在库里的 id 后写回

已删除文献的 PDF 不会被下载，避免白流量。

## 5. 并发写

两台机器同时同步时，可能出现：A 读到版本 N，B 也读到版本 N，两人都写，后写的覆盖前者。

处理方式是 `PUT` 时带 `If-Match`，服务端发现版本已变会返回 412。收到 412 就重新拉取、重新合并、再写一次，最多重试 2 次。仍失败则报「另一台设备正在同步，稍后再试」，不静默丢弃。

弱验证器（`W/"..."`）不能用于 `If-Match`，会永远 412，所以发送前过滤。

## 6. 远端布局

```
<用户填写的地址>/summa/library.json      文献库（含墓碑）
<用户填写的地址>/summa/pdf-index.json    有原文的 id 列表
<用户填写的地址>/summa/files/<id>.pdf    原文
```

应用启动同步时用 `MKCOL` 建目录，405 视为「已存在」。用户填的地址必须是已存在的共享文件夹，否则 409——不会替用户在服务器上递归建父目录。

## 7. 安全边界

- 认证只用 HTTP Basic（WebDAV 的通用方式），因此**地址必须是 HTTPS**，否则密码在网络上是明文
- 群晖默认自签名证书，提供「接受自签名证书」开关（`danger_accept_invalid_certs`），不开的话 TLS 握手会直接失败
- 密码明文存在本机 `config.json`，与 API Key 的处理方式一致。没有接系统钥匙串，是刻意的取舍：多一个依赖就多一处 viber 开发修不了的地方

## 8. 已知限制

1. **没有逐字段合并**。同一篇的标签和笔记在同一时间段内被两台机器分别修改，只有一半能保住。
2. **墓碑会缺席**。如果用户手动编辑 `library.json` 删记录（而不是用界面删除），不会产生墓碑，那篇会被同步回来。
3. **首次全量同步 PDF 会很慢**。几十 GB 走 WebDAV 需要很长时间，且中断后下次会接着传（已传的判断依据是 `pdf-index.json`），但单次命令没有断点续传。
4. **没有多用户**。同一份远端库只能对应同一个人，不支持共享库。
5. **没在 Windows 上实测过**。逻辑与平台无关，但路径拼接和字体渲染的差异需要实际验证。

## 9. 验证情况

已实测（本地 WebDAV 服务 + 打包后的真实应用，独立 bundle identifier）：

| 场景 | 结果 |
|---|---|
| 首次同步上传 | 远端生成 `library.json`，路径字段已清空 |
| 两台各加一篇 | 双方均为 2 篇，无覆盖 |
| 一台删除后另一台同步 | 双方均为删除后的状态 |
| 被删文献的旧设备重新上线 | 未复活，墓碑生效 |
| PDF 上传 | `files/pB.pdf` 与 `pdf-index.json` 均生成 |
| PDF 下载回填 | 文件字节一致，`file` 指向本机路径 |
| MKCOL 幂等 / ETag / If-Match 412 / 404 | 均符合预期 |

未验证：真实群晖 NAS（协议特性一致，但证书与权限配置需要实际调试）、Windows、断电或磁盘满等异常路径。
