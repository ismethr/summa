# 同步（WebDAV）技术方案

适用版本：0.6.0

## 0. 参考

同步算法的骨架参考了 Obsidian 插件 **remotely-save** 的 v3 算法
（<https://github.com/remotely-save/remotely-save>，8.2k star，同样支持群晖 WebDAV）。
其中两条被直接采纳：

1. **三路比对**：把「上次同步成功的快照」当作第三个输入。
2. **同步状态只存本地**，不往远端写派生元数据。

本文档记录 Summa 的落地方式与差异，不是对原项目的复述。

## 1. 问题定义

Summa 的文献库是单个 `library.json`。同步要在多台机器之间保持它一致，而 WebDAV 只是一块能读写文件的网盘——没有变更流、没有合并语义、没有事务。

两种最直觉的做法都不成立：

| 做法 | 问题 |
|---|---|
| 比时间戳，新的整库覆盖旧的 | 两台各加一篇，后同步的那台把先同步的整篇覆盖掉，**静默丢数据** |
| 删除写墓碑，墓碑优先于存在 | 「A 机删了、B 机改了」时，B 的修改被无声丢弃（0.5.0 的做法，已废弃） |

根因是同一个：**只看两边「有什么」，无法判断「本地没有」是「删掉了」还是「从来没有过」**。前者要删远端，后者要拉下来，方向正好相反。判断错了，丢数据的方向也就错了。

## 2. 三路比对

第三个输入是**本地上次同步成功时的快照**（`sync-state.json` 里的 `snapshot`，`id → rev`）。有了它，每条记录在每一侧都能落到五种状态之一：

| 状态 | 含义 |
|---|---|
| `Nowhere` | 快照里没有，现在也没有 |
| `Created` | 快照里没有，现在有 |
| `Unchanged` | 快照里有，现在也有，`rev` 没变 |
| `Modified` | 快照里有，现在也有，`rev` 变了 |
| `Deleted` | 快照里有，现在没有了 |

再按 5×5 矩阵决定动作：

| 本地＼远端 | Unchanged | Modified | Deleted | Created | Nowhere |
|---|---|---|---|---|---|
| **Unchanged** | 保留 | 拉取 | 删本地 | 拉取 | 保留 |
| **Modified** | 保留本地 | **冲突** | 保留本地 | 保留本地 | 保留本地 |
| **Deleted** | 删远端 | 拉取 | 丢弃 | 拉取 | 丢弃 |
| **Created** | 保留本地 | **冲突** | 保留本地 | **冲突** | 保留本地 |
| **Nowhere** | 拉取 | 拉取 | 丢弃 | 拉取 | 丢弃 |

两处非直觉的格子是刻意的，也是相对 0.5.0 的核心修正：

- **`Modified × Deleted` 保留本地**。本地改过说明用户还要它；远端那次删除很可能是在另一台机器上误操作。
- **`Deleted × Modified` 拉取远端**。对称地，远端改过说明它还有价值。

0.5.0 用墓碑时，第一格会直接丢弃修改。

## 3. 冲突：保留两份，不静默取胜

`Modified × Modified` 意味着同一篇在两台机器上都改过。自动挑一个等于替用户做决定，而文献笔记是用户自己整理的东西，丢了没法恢复。

处理方式：

1. 按 `rev` 决胜，`rev` 相同则比较序列化内容。**两端必须算出同一个结果**——否则 A 保留本地、B 也保留本地，同步几次后两边各有一份「原件」，副本越滚越多。
2. 胜者保留原 `id`，败者变成副本：`id` 为 `{原id}c{败者rev}`，标题加后缀「（冲突副本）」。
3. 副本的 `id` 由败者的 `rev` 决定，所以两端算出的 `id` 相同；下次同步会被识别成「同一篇」而不是再生成一份。

`rev` 相同但内容不同（时钟偏差、同毫秒修改）时用内容字符串做稳定决胜，保证确定性。

## 4. `rev` 从哪来

`Paper.rev` 是毫秒时间戳，写入点**只有一个**：`commit_library()`。它在每次写库前逐篇比对序列化结果，内容变了就刷新 `rev`。

之所以集中在一处，是因为不能指望每个命令自己记得刷新——漏掉一处，表现就是「这台机器的修改被另一台覆盖」，而这类问题极难定位。

老数据没有 `rev`，用 `added` 兜底（`sheet_rev = max(rev, added)`）。两者都是毫秒时间戳，可直接比较。

## 5. 快照丢失时会怎样

用户删了 `sync-state.json`、或者升级前从没用过同步（首次同步），快照为空。这时无法判断删除，因此退化为：

**并集 + 较新者胜，既不删本地也不删远端。**

这个选择是保守的：宁可多留，不可错删。代价是删掉的文献可能在快照重建后被拉回来一次。

另外，快照为空时会**强制拉一次远端**，即使 ETag 显示没变。否则会把本地 `rev` 当成远端状态写进快照，下次同步全部误判为「远端改过」。

## 6. 删除保护

一次同步要删除的数量超过 `max(12 篇, 总量的 30%)` 时**直接中止**并报错，不落盘。

正常使用不会触发。它防的是异常情况：另一台设备的库被重置、远端 `library.json` 被误改、本地库被清空、或者代码有 bug。这类事故的后果是整库消失，值得设一道硬闸。

判断基准是**快照**而不是「本次合并删了几条」。因为远端没变时会跳过合并，此时本地库若被清空，会直接把空库推上去——这条闸必须在这条路径上也生效。

注意阈值是「超过 12 篇**且**超过总量 30%」。小库（十几篇）删光了也不会触发，因为那与正常操作无法区分。

被拦下后的恢复方式：如果本地确实丢了，退出应用、删掉 `sync-state.json`、再同步一次，会用远端内容重建本地库（走 §5 的退化路径）。

## 7. 流量控制

同步每次开应用都跑，不能每次都全量传输。

- **远端有没有变**：`HEAD` 取 `ETag`，与上次记录比较；服务端不返回 `ETag` 时退回 `Last-Modified`
- **本地有没有变**：把要上传的内容做 FNV-1a 哈希，与上次记录比较

两边都没变就跳过整个传输。不用 `PROPFIND`，因为它要解析 XML，各家命名空间实现差异会带来无谓调试成本。

## 8. PDF 原文

PDF 单独存放，靠 `pdf-index.json` 记录远端有哪些 `id` 的原文，而不是逐篇 `PROPFIND` 或 `HEAD`——几百篇文献会产生几百个请求，坚果云这类有频率限制的服务会直接失败。

索引是**纯缓存**：丢了最多重传一次 PDF，不影响正确性。这与参考项目「不往远端写派生元数据」的主张略有出入，理由是 `summa/` 目录完全由本应用管理，用户不会手动往里放文件，索引不会与用户操作冲突。

流程：

1. 读索引（一次 GET）
2. 本地有、远端没有 → 上传
3. 远端有、本地没有、且这篇仍在库里 → 下载并回填 `file`
4. 索引收窄到仍在库里的 `id` 后写回

## 9. 路径不上传

`file` 和 `source` 是本机绝对路径。上传前清空，下载后按 `files/{id}.pdf` 重建。

不清空的话，A 机的 `/Users/a/.../p123.pdf` 会漂到 B 机覆盖掉本来能用的路径，表现是「同步之后 PDF 打不开了」。

合并时还要防反向污染：本地已有可用路径时，即使采用了远端版本，也要把本地路径补回去。

## 10. 并发写

两台机器同时同步时，`PUT` 带 `If-Match`，服务端发现版本已变返回 412。收到 412 就重新拉取、重新合并、再写，最多重试 2 次。仍失败则报「另一台设备正在同步」，不静默丢弃。

弱验证器（`W/"..."`）不能用于 `If-Match`，会永远 412，发送前过滤。

## 11. 远端布局

```
<用户填写的地址>/summa/library.json      文献库
<用户填写的地址>/summa/pdf-index.json    有原文的 id 列表（纯缓存）
<用户填写的地址>/summa/files/<id>.pdf    原文
```

同步时用 `MKCOL` 建目录，405 视为「已存在」。用户填的地址必须是已存在的共享文件夹，否则 409——不替用户递归创建父目录。

## 12. 安全边界

- 认证只用 HTTP Basic（WebDAV 的通用方式），因此**地址必须是 HTTPS**，否则密码在网络上是明文
- 群晖默认自签名证书，提供「接受自签名证书」开关；不开会 TLS 握手失败
- 密码明文存在本机 `config.json`，与 API Key 一致。没有接系统钥匙串是刻意的取舍：多一个依赖就多一处难修的地方

## 13. 已知限制

1. **没有逐字段合并**。冲突时整条记录保留两份，而不是把标签取并集、笔记取更长的。可预测优先于聪明。
2. **首次全量同步 PDF 很慢**。中断后下次会接着传（已传的判断依据是索引），但单次命令没有断点续传。
3. **远端孤儿 PDF 不清理**。文献删除后，远端的 `files/<id>.pdf` 会留着。不自动删是为了避免一个 bug 造成批量误删。
4. **没有多用户**。同一份远端库只能对应同一个人，不支持共享库。
5. **没在 Windows 上实测**。逻辑与平台无关，但路径与字体渲染差异需要实机验证。

## 14. 验证情况

已实测（本地 WebDAV 服务 + 打包后的真实应用，独立 bundle identifier）：

| 场景 | 结果 |
|---|---|
| 首次同步上传 | 远端生成 `library.json`，路径字段已清空 |
| 两台各加一篇 | 双方均为 2 篇，无覆盖 |
| 一台删除后另一台同步 | 双方同步为删除后的状态 |
| 被删文献的旧设备重新上线 | 未复活 |
| **两边改同一篇** | **两端都得到「原件 + 冲突副本」，副本 id 一致** |
| PDF 上传 / 下载回填 | 文件字节一致，`file` 指向本机路径 |
| MKCOL 幂等 / ETag / If-Match 412 / 404 | 均符合预期 |

单元测试覆盖矩阵中每种状态组合，以及冲突副本的确定性。

未验证：真实群晖 NAS（协议一致，证书与权限配置需实机调试）、Windows、断电或磁盘满等异常路径。
